# Changelog

All notable user-facing changes to Antseed packages are documented here.

This project uses selective package publishing. Each release entry lists the published packages affected by that release.

## Unreleased

### Added

- Sellers: alerts. A seller sends a Telegram message or a webhook (`{ text, content, seller, event }`) when a model is withdrawn after failing health checks or restored, the gas balance drops below the minimum or recovers, the seller restarts after an unexpected exit, or it serves nothing for `idleMinutes`. Recoveries are sent only after their alert went out, the same alert goes out at most once per cooldown (30 minutes by default, also across a recovery, so a flapping model alerts once; crash alerts keep it across restarts), and the lowest severity sent is configurable. `antseed seller alerts test` sends a test message. The events are also kept in `<data dir>/seller-events.jsonl` (rotated at 1 MB).
- `antseed metrics serve --role seller`: model health (`antseed_seller_model_advertised`, `_consecutive_failures`, `_last_status_code`, `_last_probe_timestamp_seconds`) labelled by the provider's name in your config (`provider`), its `plugin` and `service` and gas (`antseed_seller_gas_balance_eth`, `_min_balance_eth`, `_depleted`) from the running seller.
- Seller dashboard and the console's Seller **Logs**: clicking a request opens it in full: the upstream's error for a failed request, model and upstream, buyer, latency, input, cached input and output tokens (reported or estimated), cost, the signed usage receipt and the buyer's check of it, the request's place in its session with the session totals, and the buyer's payment channel at the time (status, delivered of authorized, settled). `antseed seller logs` shows an Id column and the failure reason; `antseed seller logs --id <Id>` prints the same detail. Console API: `GET /seller/logs/:id`.
  - Metering: sellers now record a short upstream error for failed requests and the cached input tokens (`metering_events.error`, `metering_events.cached_input_tokens`, metering migration 7); older rows have none.
- CLI: `antseed seller dashboard` opens a local page for a seller: running or stopped, uptime, requests and revenue today and per day for 14 days, active channels, the gas balance, every service's health-check status with its last upstream error (a withdrawn service is marked), recent events, payments from the local channel ledger, and where alerts go. It is the gateway console in a seller-only mode, on `127.0.0.1:3120` by default, opened with a session link the command prints (for a remote server, tunnel the port with `ssh -L`). Docs: **Provide → Monitoring**.
- Seller dashboard and the console's Seller pages: a **Logs** page lists every request the seller passed to an upstream, served or failed (time, buyer, model, status, tokens, latency, receipt cost), newest first, filtered by model, buyer, time or failures, with older pages read by keyset on the timestamp index (fast on multi-GB metering databases; a filtered page looks through at most 5,000 requests and then offers to look further back); **Events** on the same page is the event journal.
  - Metering: sellers now record the requested model on each request (`metering_events.service`, metering migration 6); older rows have none.
  - Metering: sellers now record each request's protocol request id (`metering_events.request_id`, metering migration 8), so a one-off paid request's detail shows its own one-off channel; seller payment totals include one-off channels.
  - Metering migration 9 indexes `usage_receipts(session_id, event_id)` so seller request-log pages stay fast in long sessions. `seller.alerts` is validated with the rest of the config and kept when other commands save it; a numeric Telegram `chatId` is accepted.
- CLI: every seller dashboard view and edit is an `antseed seller` command on the same service code, each with `--json`: `events`, `usage`, `logs`, `market`, `reputation`, `promote [--card]`, `verify`, `settings` / `settings set`, and `alerts` / `alerts set` / `alerts test [--channel]` / `alerts find-chat` (secrets from stdin only). `antseed seller status` adds model health, gas, alerts and the seller's chain calls per minute, and reads registration and stake through the same service as the dashboard (its `--json` `onChain` no longer has `mode`; it adds `registryBound` and `minPoolStake`).
- Chain reads: the seller dashboard, `antseed seller …` commands, `antseed network browse` and the seller's gas check go through one shared RPC provider per process (duplicate calls merged, concurrent reads batched into Multicall3, back-off on errors and 429s), and are counted per source (`antseed_rpc_calls_total{source,process}` in `antseed metrics serve`, and in `antseed seller status`). On-chain standing is cached until the staking epoch ends (at most 30 minutes) and only read on demand: about 24 HTTP requests per read instead of about 94. A well-funded seller (20 times the minimum gas balance or more) checks its balance every 10 minutes instead of every minute. `antseed metrics serve --include-chain` reads balances at most once a minute in one batched call.
- CLI: `antseed config set` and `antseed config seller|buyer set` change only the key you set in the config file (atomically, previous file kept as `config.json.bak`) instead of rewriting the whole file with defaults.
- Seller dashboard and the console's Seller **Settings**: the free tier. Each pricing row shows the free tier buyers of that model get (its own program, or the seller-wide one on a free model) and edits the model's own program (per address, per IP, window, stakers only); the seller-wide free tier gains stakers only and staked tiers (network default, custom or none). CLI: `antseed seller settings` lists each model's free tier, and `seller settings set` takes `--model-free-tier`, `--free-stakers-only` and `--free-stake-tiers`. Console API: `SellerServicePricing` gains `paid`, `freeTier` and `ownFreeTier`, `SellerSettings` gains `defaultStakeTiers`, and pricing entries take a `freeTier`.
- Seller dashboard and the console's Seller pages: **Market** compares each model you sell with every other seller of it (count, cheapest and median price, your rank by blended price, distance from the median, every seller with trust, TEE and load), marks models only you offer and lists the models others sell that you don't. **Reputation** breaks your trust score into its parts with a next step for each, plus on-chain standing (agent, eligibility, pool stake and power, stakers, pending rewards, volume, buyers, ghost rate). **Promote** has your explorer profile link, a downloadable seller card (SVG or PNG), pinned `<peerId>@<model>` ids, and domain and GitHub verification setup with the proof to publish and a live check; claims are saved to `seller.verifications`. The network snapshot comes from the gateway's buyer, a co-located buyer, or a short-lived discovery, refreshed in the background every 15 minutes. Console API: `GET /seller/market`, `GET /seller/reputation`, `GET /seller/promote`, `POST /seller/promote/check`, `PUT /seller/promote/verifications`.
- Seller dashboard and the console's **Seller** page: an **Alerts** panel sets up Telegram (paste the bot token, **Find chat** lists the chats that messaged the bot, **Send test**) and a webhook, with the lowest severity sent, the quiet-seller alert and the repeat interval. The bot token and webhook URL are saved in `<data dir>/secrets/seller-alerts.json` (0600), never in `config.json`, and never sent back to the browser. The other alert settings saved there go to `<data dir>/seller-alerts.json`, layered over `seller.alerts` in `config.json`, so alerts can be set up even when `config.json` is read-only; an environment token (`seller.alerts.telegram.botTokenEnv`, default `ANTSEED_ALERTS_TELEGRAM_TOKEN`) still takes precedence. A running seller picks up alert changes, `idleMinutes` included, within a few seconds without a restart. A **Settings** panel edits display name, max concurrent buyers, refused countries, health and gas checks, free tier limits and per-service prices: validated like the seller's own config load, unknown fields kept, the previous file kept as `config.json.bak`, applied on the next restart. A read-only config (such as a Kubernetes ConfigMap mount) shows the settings read-only; alerts stay editable. Console API: `GET/PATCH /seller/settings`, `PATCH /seller/alerts`, `POST /seller/alerts/test`, `POST /seller/alerts/telegram/chats`; console edits are audited.
- Gateway console: **Seller** pages (organization owners and admins) when the gateway host also runs a seller, found in the gateway's data directory or `ANTSEED_SELLER_DATA_DIR`. Hidden otherwise. Console API: `GET /seller/status`, `/seller/events` and `/seller/usage` (org admins and management tokens).
- Seller (`@antseed/node`, CLI): staked free tier. Buyers staked on a seller get a larger free allowance by staking power (ANTS × epochs of lock remaining). Default `seller.freeTier.stakeTiers`: 520,000 / 2,600,000 / 10,400,000 power (≈10k / 50k / 200k ANTS locked for a year) earn 5×, 20× and unlimited; `[]` turns tiers off. The seller adds up the power of the buyer and of every staker that signed a free-tier delegation to it (EIP-712 `FreeTierDelegation(staker, buyer, expiresAt)`, domain `AntseedFreeTier` v1, sent in the `x-antseed-free-tier-delegations` request header and in the free-usage open's optional `freeTierDelegations` field so channel admission counts delegated stake from the first request, up to 8, verified locally and stripped before the provider). Only stake in that seller's own pool counts. Usage is counted on the staked positions, so buyers behind the same stake share one allowance and a transferred position keeps its used allowance; staked requests skip the per-IP limit and don't count toward unstaked buyers' base limits. Lookups are cached for 10 minutes and fall back to the base limits when the chain can't be read. Limits and tiers are announced as signed `free-tier.v1.*` peer capabilities (no metadata version bump). Free-tier 429s carry `limitedBy: "stake"` for staked owners, plus `stakeTiers` and `stakePower` when tiers are on. Metering migration 4 adds `free_tier_usage.staked` and the `free_tier_position_usage` table.
- Seller (`@antseed/node`, CLI): per-model free-tier programs. A zero-priced service can set its own `seller.providers.<p>.services.<s>.freeTier` (base limits, `windowMs`, `stakeTiers`) in place of `seller.freeTier`, with its own counters; services without one keep the seller-wide program, or stay unlimited when there is none. `stakersOnly: true` serves a program only to buyers whose stake reaches a tier: others get a 429 with `limitedBy: "stake_required"`, `limit: 0` and `stakersOnly: true`, and the base limits are the allowance the tier multipliers apply to. Each program picks its own tier from the buyer's pooled staking power. Service programs are advertised as `free-tier.v1.m<8 hex of keccak256(serviceId)>.*` capabilities (`s1` = stakers only, `t1` = same tiers as the seller-wide program, so it costs one string); programs that don't fit the 16-capability limit are still enforced but not advertised, and a program whose capability strings would exceed 64 characters is rejected at config load. `SellerFreeTierLimiter`'s `maxRequestsPerAddress`, `maxRequestsPerIp` and `windowMs` remain as deprecated getters for the seller-wide program. Free-usage channels open while any program would still serve the buyer. Metering migration 5 adds a `scope` column to `free_tier_usage` and `free_tier_position_usage`.
- Seller (`@antseed/node`, CLI): stake-or-pay. A priced service's own `freeTier` is a free allowance: requests it covers are served free, without a payment channel, and the rest are paid at the listed price instead of refused (with `stakersOnly: true`, stakers get the allowance and everyone else pays). Covered responses carry `x-antseed-free-tier: covered` (the seller drops any copy its provider sends); the seller records no spend and sends no NeedAuth for them, and the buyer refuses to sign any NeedAuth from that seller for a covered request (a retry of the same request ID, or a fallback seller, is paid normally). Paid image and video offers never get the seller-wide program, and paid video has no allowance. The seller-wide `seller.freeTier` still covers only zero-priced services, and priced allowances never admit a free-usage channel. Stake tiers may now start at a 1× multiplier. Free-tier 429s also carry `baseLimit` (what tier multipliers apply to), and `antseed seller start` prints one line per program, marking priced models' allowances "then paid".
- Buyer (`@antseed/buyer-core`, CLI): a seller's free-tier 429 is rewritten from its numbers into a plain message naming the reset time and the next tier, with a `free_tier` object (`peerId`, `limitedBy`, `limit`, `windowMs`, `retryAfterSeconds`, `stakeTiers`, `stakePower`), in the client's own API format. A stakers-only refusal says how much stake unlocks the model. The gateway console shows each service's own program (`services[].freeTier`, model offers' `freeTier`); a priced service shows only its own free allowance, never the seller-wide program. A response marked `x-antseed-free-tier: covered` is expected to cost nothing. Gateway-policy routing without deposits also tries paid sellers whose model advertises a free allowance. The buyer's `/v1/models` peers carry each offer's `freeTier`; console `NetworkModel` gains `freeForStakers` and `freeAllowance`, `ChatModel` gains `freeForStakers` and its peers `freeTier`, and `free` now means free to everyone (not stakers-only). Free-tier messages name tiers in requests when the seller sends `baseLimit`; the chat cost estimate is zero for covered steps.
- CLI buyer: `antseed buyer free-tier add <code>` adds a staker's `antseed-free-tier-…` code after checking its signature, buyer and expiry; `share` opens a local page where a staking wallet on the same machine signs a delegation to the buyer (no gas, 90 days); `list` and `remove <staker>` manage them. Delegations are stored in `buyer.freeTierDelegations` and a running buyer reloads them every minute. `--identity` targets a named buyer identity.
- Gateway console API: free-tier code endpoints for workspace admins (adds and removals are audited); `Peer` and `NetworkModelOffer` gain `agentId` and `freeTier`, and the buyer's `/_antseed/peers` gains `onChainAgentId`.
- Gateway console: starred models and routers keep the order they were starred in when two are starred in the same millisecond.
- ANTS dashboard: **My positions → Share free tier** lets a staker sign a free-tier delegation for any buyer address (no gas, 30/90/365 days) and copy it as an `antseed-free-tier-…` code. It works the same standalone (`antseed ants`), from desktop Rewards → Manage staking, and on the gateway's Staking page. `#/stake?pool=<agentId>` opens a seller's pool.
- Desktop and gateway: buyers add a staker's code in desktop Rewards → Staked free tier or on the gateway's Staking → Staked free tier panel (workspace admins).
- Desktop, gateway and CLI show when a staked tier drops. Rewards → Staked free tier, the gateway's Staking panel and `antseed buyer free-tier list` list the stake each seller pool counts (the buyer's own plus shared, read live from the chain) and how it shrinks; model tooltips say what the buyer gets there and until when ("You get unlimited until Dec 14, 2026, then 1,000 a day"), and suggest max lock when the tier drops within four weeks. Tier tooltips and the share form explain that power drops weekly and max lock keeps it, that a code shares all the staker's stake in each pool until it expires, and that every buyer shared with draws from one allowance. The new browser-safe `@antseed/node/free-tier-stake` subpath (re-exported from `@antseed/node/free-tier-program`) has `freeTierOutlook`, `freeTierPowerAt`, `freeTierStakeTrend` and the `FreeTierStakeView` types, shared by desktop, the gateway console and the CLI; a max-lock change counts only from the epoch it takes effect (`maxLocked` now, `maxLockedNext` from the next epoch), and a code stops counting the second it expires. Desktop re-reads the counted stake every five minutes and when its window regains focus; `@antseed/ants` gains `freeTierStake(ctx, buyer, stakers)`; the console API gains `GET /workspaces/:id/free-tier/stake`, and peer services gain `paid` so the console treats a per-image or per-video price with zero token prices as paid; `antseed buyer free-tier list` gains `--no-stake`.
- Buyers see each seller's free tier where they pick models: desktop model pages show a free seller's limit ("1,000 free requests a day") and a **Stake for more** tooltip with its tiers; the gateway shows the same in a model's provider list and on provider pages. Only stake in that seller's own pool counts toward its tiers.
- Desktop and gateway show each model's own free-tier program, not the seller's: "Free for stakers", "Free for stakers, others pay", or a priced model's "N free requests a day, then paid", with tiers named in requests. Model lists and pickers mark **Free for stakers** and **Free allowance** models, "Free" means free to everyone, and a provider's page shows each model's program. A stakers-only refusal says how much stake unlocks the model. The ANTS dashboard and desktop Rewards mention stakers-only models.
- Desktop chat and gateway chat show a seller's free-tier 429 as a notice with a **Stake in this seller's pool** link instead of retrying.
- Docs: new [Staked free tier](/docs/staked-free-tier) buyer guide and a staked-tiers section in seller configuration; blog post introducing the program.
- Docs: per-model programs, stakers-only models and stake-or-pay allowances in seller configuration and the Staked free tier guide.

### Changed

- CLI gateway: `antseed gateway settings show` now prints the config file it read, and `antseed gateway routing preview` says which file the `Buyer config:` limits came from. `--config` and `--data-dir` default independently (`~/.antseed/config.json` and `~/.antseed`), so on a host that runs several roles — a seller on `~/.antseed`, a gateway on `--data-dir ~/.antseed-buyer` — the buyer limits shown could come from another role's file with nothing in the output saying so. When `--data-dir` holds a `config.json` that is not the file being read, both commands now say so and name the `--config` flag that would read it.

- Gateway console: while a self-hosted gateway updates itself (**Restart & update**), the console shows the current step in plain words with a one-line explanation, an elapsed timer (mm:ss), and a step bar (step N of 5): downloading, restarting the buyer, waiting for in-flight requests to finish (up to the gateway's 90-second stop timeout), starting the new gateway, and checking it. While the gateway is down mid-update, the console says "The gateway is restarting" and keeps polling until it is back, instead of showing an error. Afterwards it shows the versions it went from and to, with how long the update took. If the update fails, it shows the error, that the gateway still runs the previous version, and how to retry.
  - Gateway installer (`install-gateway.sh`): the root updater writes `phase`, `phaseStartedAt` and `phaseMaxMs` to `/var/lib/antseed-update/status.json` while it runs. Earlier readers ignore the new fields. Existing servers get step reporting the next time the installer runs; until then the console shows the timer without steps.
  - Console API: `GatewayUpdate.progress` can carry `phase`, `phaseStartedAt` and `phaseMaxMs`. `antseed update` on the server prints each step as well.

- Buyer (`@antseed/buyer-core`, CLI, desktop): with several requests in flight to one seller, a seller's catch-up payment request (its spend ran ahead of the signed amount) is now covered in full, up to the per-request limit for each in-flight request and never beyond the channel reserve. The buyer retries while the gap shrinks (at most three attempts), and if the gap stops shrinking or is still not covered returns a `payment_negotiation_failed` error instead of passing through the seller's raw 402.
- Website: the docs have search. Press ⌘K (Ctrl+K), `/`, or the navbar search button to open it. Results update as you type, tolerate typos, and cover every docs page and section. The index is built with the site and searched in the browser, with no external service.
- Website: the **Set up gateway** button in the navbar has its right padding back.
- Website: the Hermes integration guide is rewritten so a Hermes agent can follow it on itself. It installs the `hermes-antseed` skill, checks that the buyer is running and funded, picks models that actually answer, adds Antseed as a provider and tests it before making it the default, and ends with `/restart`. Config changes go through `hermes config set` only. The **Run this first** box no longer generates a throwaway `ANTSEED_IDENTITY_HEX`; it says to back up `~/.antseed/identity.key` and keep the buyer running as a service.
- Skills: `hermes-antseed` is rewritten to match, and passes Hermes' skill security scan.
- CLI buyer: the local buyer proxy only answers local clients. A request whose Host is a hostname other than `localhost`, or that a browser sends from a page other than a local one (an `Origin` other than a loopback address or `file://`, or a cross-site fetch), gets `403 non_local_request`. CLI tools, SDKs and local pages are unaffected, and IP-address hosts (such as the WSL relay's) still work. The API-key gateway and system proxy no longer pass the client's `Origin`, `Referer` and `Sec-Fetch-*` headers on to the buyer.
- Desktop: the chat's per-seller usage stats are read through the main process instead of from the page.

- Gateway console: **Deposits** on **Wallet & Funding** lists the money that came into the workspace: each transfer of USDC to the workspace wallet, and each direct deposit from a connected wallet. Each has a printable confirmation and can be approved.
  - A transfer is listed once its USDC starts moving into the credits, usually within a minute. It is the transfer the move's own on-chain check found (USDC sent to the wallet in the half hour before), so the list needs no extra search of the chain, and transfers made before this change are listed too. A transfer the check missed can be added with **Add a past deposit**.
  - The automatic moves (sweeps) from the wallet into the credits are no longer listed. One transfer is often moved in several small pieces, so listing them counted the money more than once. A sweep approved earlier stays listed with its approval, for the amount it moved; the transfer it came from is approved on its own.
  - New USDC minted into the wallet is labelled **Exchange or card (new USDC)** instead of **Card purchase**. Exchange withdrawals (such as Coinbase on Base) arrive the same way as card purchases.
  - **Add a past deposit** takes the transaction that sent USDC to the wallet. A pasted sweep is refused, with a request for that transaction instead.
  - Gateway database migration 14 rebuilds the deposits table to accept the new `transfer` kind. Console API: `DepositConfirmation.kind` can be `transfer`.
- CLI buyer and desktop: automatic deposits move USDC from the deposit wallet into the credits in fewer, larger pieces.
  - Every move credits at least the contract's minimum deposit ($1), not only the first one, so small leftovers wait for more USDC instead of each paying the relay fee.
  - When the wallet holds more than the credit limit allows, the top-up waits until half the limit is free (at least $1), instead of moving a dollar or two every time spending frees some room. When the credits free to spend can no longer open a session (the rest is reserved in open sessions), the top-up goes as soon as $1 of room is free.
  - The desktop's funding status follows the same rules.

- Gateway console: a model's providers (Models, Chat and **Try a request**) are listed in the order your routing policy tries them, showing the sellers **in range**. An **In range / All** switch (or **Show them** under the list) adds the sellers your policy filters out, dimmed, each with the reason (for example "trust 42 below 70" or "over input price cap"). Every seller has **Allow…** for the filtered ones, and **Prefer for this model…** and **Block…** in its ⋯ menu, applied at the level you pick. On **Providers**, picking a model adds a **Routing** column and sorts by it.
- Gateway console: on the **Routing** page, **Try a request** is now a button that opens the route preview in a dialog, so the page starts with the rules themselves. After you try a model, each level of **Rules that apply** still says how many of its sellers it keeps out.
- Gateway console: the routing policy editor and **Settings → Buyer** have one quality score, the minimum trust score, with an ⓘ that explains what it is made of. That is service history (up to 50), recognized usage (20), staking power (10) and verified identity (20), plus 5 for a free model; a proven wash trader scores 0. The separate minimum-reputation slider is gone. A policy or buyer config that still sets a reputation minimum says so, with **Remove it**.
- Gateway console: the routing policy editor (gateway default, organization, workspace, member, key and preset policies) is laid out as one column of labelled groups: Sellers, Quality, Price limits, Models and Ranking, each with a line of help. A **What this level does** box at the top states the policy in sentences as you edit it, with how many sellers can still serve. The template buttons became one **Start from…** menu, and price limits are no longer folded away.
- Gateway console: peer lists are called **seller lists** in the console and are managed under **Routing → Seller lists**, which shows each list's sellers by name. **Manage seller lists** in the policy editor opens them without leaving the editor, and clicking a list's name there opens that list to edit (or, for members, to see its sellers). Policies name a list with its size, for example "the “preferred” seller list (8)". **Providers** links there instead of holding the lists. The CLI and API still call them peer lists.
- Gateway console: in seller selection (Models, Chat and Try a request), each seller shows one line: success rate, first token, speed, traffic share and expected cost. Badges appear only for exceptions: failing, cooling down, new, a new payment channel, or at capacity.
- Gateway console: the **Routing** page is rebuilt around one question: where does a request for this model go, and why?
  - **Try a request** at the top replaces the route preview's free-text model field with a searchable model list. It starts on a model (your first starred one, or else the most offered one) and updates as soon as you pick a model or a key, member or preset. It lists the sellers in the order they are tried, with the numbers routing ranks them by. Each seller it does not use shows the level and the rule that keeps it out, for example "Gateway default blocks it" or "Buyer config requires trust 60+ (it has 55)".
  - **Rules that apply** replaces the **Gateway default** / **This workspace** tabs with one numbered list of every level: buyer config, gateway default, organization policy, workspace policy, then members, keys and presets. Each level is written in plain sentences, with **Edit** or **Add rules** right there, and says how many of the tried model's sellers it keeps out. The list ends with what the levels add up to for the workspace.
- Gateway console: see which sellers automatic routing picks for each model, and why.
  - **Models → a model** and the new ⓘ button next to the model in **Chat** open the same model panel. Its new **Seller selection** section lists the sellers in the order routing tries them. It says how they are ordered: expected cost of a good answer, trust, or the policy's sort. Each seller shows its expected cost per good answer, its success rate and how many recent requests that rests on, first token and speed, its share of the traffic, payment channel state and load. A failing or cooling-down seller shows its last error, and org admins can **Reset history**. Sellers routing skips are listed under **Not used** with the reason. In the chat, **Pin** pins the conversation to a seller.
  - The chat's seller picker shows each seller's success rate and traffic share.
  - Each model-routed request in **Logs** shows **Why this seller**: how the seller was picked and what the buyer had seen of it then. The pick is one of: drawn from the sellers sharing the traffic, best on its own, kept for the conversation, a probe, a failover, or the policy's order.
  - Gateway database migration 13 adds the record. Requests logged earlier, and pinned requests, have none.
  - Console API: route-preview candidates add `selection`, `GET /requests/:tag` adds `routeSelection`, and `POST /routing/seller-history/reset` clears a seller's record.
- CLI buyer: `GET /_antseed/route-preview` returns a structured `selection` for each eligible seller: expected cost, success rate, observations and whose record they are, speed, last failure, ordering, traffic share, channel and load.
  - The preview now keeps the real traffic-sharing pool instead of ranking as if there were none.
  - Its "shares traffic" reason appears only when the buyer actually spreads traffic. It does not when it ranks by trust, by a policy sort, or by a route chain.
  - Model-routed responses carry `x-antseed-route-selection` (base64url JSON): the serving seller's rank, how it was picked, and the same numbers.
  - Sellers cannot set or forge this header; the buyer strips it from their responses.
  - `@antseed/node`: `SellerHealthBook.hasRecord`.
- Gateway console and CLI gateway: requests a routing service ranked now show the router, the model it picked and its fee. The request log used to record only the router's service id as the model and the seller that answered, so a request through a router (for example Levanto) looked like any other request to that seller. Logs now show `levanto-router → opus-5.5`, and a request's details add **Router** (its name, peer id, service, and which of its recommendations served the request, how many were tried when all refused, or that the ranking failed) and **Routing fee** next to **Cost**, which still includes the fee. Logs can be filtered by router, Activity can group by router, and the CSV export adds `servedModel`, `routerPeerId`, `routerService`, `routerRank` and `routingSpent`. A request whose ranking failed no longer lists the router as its seller. `antseed gateway usage --group-by router`, `antseed gateway logs --router <peerId>` and `antseed gateway logs show` do the same on the command line. `GET /console/api/requests` adds `servedModel`, `router` (`peerId`, `service`, `rank`) and `routingSpent`; `/usage` and `/requests` accept `router=<peerId>` and `groupBy=router`. Requests logged before this version have no router recorded.
- CLI buyer: responses to requests a routing service ranked carry `x-antseed-router-peer-id`, `x-antseed-router-service` and `x-antseed-router-rank` (the recommendation tried last, 1 = the router's first pick), including failed rankings, and streamed responses now carry `x-antseed-service` like non-streamed ones. The spend feed marks a ranking's spend `purpose: "routing"`.

Stars are saved per console member (or API-key session) on the gateway, so they follow you across browsers. - `@antseed/node`: new `@antseed/node/model-metadata` export (`modelMetadataFor`, `modelTagsFor`, `availableModelTags`), the release-owned model tag registry the desktop app used, now shared with the gateway.
- CLI buyer: automatic routing now learns from its own traffic which sellers serve each model well, instead of always sending every request to the cheapest seller. For each seller and model the buyer keeps a time-decayed record of successes, failures, time to first token and output speed (half-life 15 minutes, saved in `buyer.state.json`), and ranks sellers by the expected cost of one successful answer: price plus the time it takes, divided by the chance it succeeds. A seller that keeps failing drops behind within a few requests and comes back as soon as it serves again; there is no fixed cooldown. With no record yet, the order is price order as before, and trust stays a filter, not a ranking.
  - A failure is anything that does not answer: an error status, a dropped or timed-out request, an empty answer (a 200 with no text and no tool call), or a seller-signed receipt that does not match the response. A client error or an empty answer can be the request's own fault, so the buyer asks one more seller, and only if that seller answers does the failure count. A seller's record on one model counts, at half weight, for models it has not served this buyer yet.
  - Traffic is spread across sellers within 30% of the best expected cost, weighted toward the cheapest, instead of all going to one. Requests of one conversation stay on one seller so its prompt cache keeps working: conversations identified by a session id (Claude Code, Codex, OpenCode) or an OpenAI `prompt_cache_key` always map to the same seller while it stays healthy.
  - Spreading stays on sellers the buyer already has an open payment channel with (or free ones); a new channel is reserved only when that seller is clearly better or needed for failover. A seller already holding as many of the buyer's requests as it advertises it can take (`maxConcurrency`) is skipped as a first choice.
  - When another seller can take over, the buyer stops waiting for a seller that has not started answering within about four times its usual time (30 s to 2 min) and tries the next one.
  - A small share of standalone requests tries a seller the buyer has no recent data on, among those it already has a channel with, so recovered sellers are noticed.
  - The route preview lists each seller's success rate, speed and whether it shares traffic; `GET /_antseed/peer-health` adds `sellerHealth`, and `POST /_antseed/peer-health/clear` also resets a seller's record. A gateway key's explicit **Cheapest**, **Most trusted** or **Lowest latency** sort and route chains still apply, with failing sellers tried last.
- Node: `AntseedNode` emits `response-auth` with the verdict on each seller-signed response receipt, and exports the routing model as `SellerHealthBook` and `orderAdaptiveRoutes`.
- Node: `FileIdentityStore` takes an optional `scrypt` cost for the keys it encrypts; the default is unchanged (`DEFAULT_SCRYPT_PARAMS`).

### Fixed

- Sellers: a model withdrawn after failing health checks now keeps its real upstream error. With several upstreams on the same provider plugin (for example four OpenAI-compatible upstreams), the health checker also probed a withdrawn model through the other upstreams, which refused it, so its last error read "not in the allowed list" instead of the upstream's reason.
- `antseed seller status`: **Earnings today** and **Tokens today** come from the metering ledger; they always showed $0.00 and 0.
- Sellers: a `seller.gasCheck.minBalanceEth` below 0.000001 ETH (written as `1e-7` in JavaScript) no longer stops `antseed seller start` with "invalid FixedNumber string value".
- `antseed seller settings set --price <model>=<in>/<out>` keeps the model's cached-input price instead of removing it; `/none` removes it.
- CLI `metrics serve` (seller role): a scrape no longer sums the whole metering ledger. On a long-running seller those all-time queries read gigabytes and took minutes, stalling the seller's own database writes until its liveness probe restarted it, and blocking the exporter's `/healthz`. The exporter now opens `metering.db` read-only and keeps running totals, reading at most 100,000 new rows per table per scrape (about 0.2 s on a 4.7 GB ledger). After the exporter starts, the `antseed_seller_metering_*` and `antseed_seller_receipt_revenue_*` series appear once it has read the whole ledger; `antseed_seller_metering_backfill_complete` reports when that is.
- Seller and buyer (`@antseed/buyer-core`): response-auth hashes request and response bodies with a WASM Keccak-256 (`hash-wasm`) instead of the pure-JS one, about 25× faster with the same digests. On a 2-vCPU seller, hashing a single multi-MB request body took over a second on its only thread, so a stream of large requests kept the seller at 100% CPU until its liveness probe restarted it. The pure-JS hash is still used while the WASM one loads.
- Seller (`@antseed/node`): requests for a free (zero-priced) model are no longer parsed and token-counted to estimate a cost that is always zero. On multi-MB request bodies this was the next-largest share of the seller's CPU.
- Node (`@antseed/node`): a `start()` that fails partway (for example the DHT failing after the payment store and RPC monitor opened) now releases what it opened, so a retry in the same process starts clean, and `stop()` removes the idle-settlement listener, so a restarted seller settles each idle session once. The gas monitor drops a balance reading still in flight when it stops, and services withdrawn at start (a provider whose sign-in failed) are reported through `onChange` when the health checker starts.
- Node (`@antseed/node`) API: `MeteringStorage.listEventsPage` (keyset request-log pages; a filtered page walks at most `scanLimit` rows and returns `scannedTo` to continue from) and `getEventDetail` (null for a prefix matching more than one request); `ChannelStore.getRoleTotalsByStatus`; `appendSellerEvent` and `readSellerEvents`; `NodePaymentsConfig.readProvider`; `NodeConfig.identity` (an identity used as is, ahead of `ANTSEED_IDENTITY_HEX` and the stored key); `GasHealthMonitorConfig.relaxedIntervalMs`; `providerId` on `ModelHealthEvent` and `ServiceHealthSnapshot`.
- Metering migration 10 adds the free-tier columns of migrations 4 and 5 where a database recorded those versions without running them (a pre-release build used the same numbers); it changes nothing elsewhere.
- Seller (`@antseed/node`, `@antseed/buyer-core`, CLI): a seller no longer exits when an RPC request times out while it waits for one of its transactions (channel reserve, top-up, settle or close, free-usage records) to be mined. ethers' `tx.wait()` polled for the receipt from a block listener whose failures nobody handled, so a single timed-out read crashed the process and broke in-flight requests, such as video jobs waiting for their payment channel. Transactions are now waited on by polling the receipt directly, retrying failed reads; a reverted transaction still fails with `CALL_EXCEPTION`, and one whose nonce was taken by another transaction fails as dropped or replaced.
- Gateway console: models and routers starred within the same millisecond are listed in the order they were starred, instead of alphabetically.
- CLI buyer and gateway: image edits (`POST /v1/images/edits`, a multipart form) honour a `peerId@model` model. The buyer pins that seller and sends the bare model, as it already did for JSON requests. Before, it looked for a seller serving the whole `peerId@model` name and answered `model_not_found`.
- CLI buyer and gateway: automatic routing sends an image edit only to a seller that advertises the `image` parameter for the model, as if the request carried `x-antseed-required-parameters: image`. When none does, the request gets `422 required_capability_unavailable` instead of a 404 from a seller that only takes text. A pinned seller is still used as pinned.
- CLI: `antseed verifier submit` reads verification events in 1,000-block chunks, so it works with RPC providers that limit log query ranges.
- Sellers: payment transactions sent from one wallet by different contract clients (for example a free-usage `record()` and a video channel `reserve()`) no longer pick the same nonce. The second one used to fail with "replacement fee too low", so the seller never opened the video payment channel and the buyer got `buyer-reserve-topup-timeout`. Nonces are now tracked per wallet and chain across the whole process, each transaction is sent before the next one takes a nonce, and a transaction that fails before it is sent no longer makes the next one reuse a nonce that is still pending.
- Gateway console and desktop: **Close channel** (asking the seller to close) is offered only on the channel the buyer is using with that seller. Older channels with the same seller that are still open on-chain offer **Close on chain**. Before, the request named only the seller, so it could never close the row you picked and could close the live channel instead. The close request now carries the channel id, and the buyer refuses one that is not the live channel.
- Gateway console: asking a seller to close a channel no longer fails after 5 seconds with "The buyer is not reachable: The operation was aborted due to timeout". The gateway now waits past the buyer's one-minute wait for the seller's answer.
- Gateway console: a payment channel that never reached the chain is shown as `expired` and stops counting as open once its reserve deadline passes.
- Sellers (`@antseed/node`): a video channel whose top-up failed is no longer left open on-chain with the buyer's reserve and unknown to the seller. The seller records the channel as soon as it is reserved, retries the top-up while its RPC node has not yet seen the reserve, and keeps retrying the release if that fails too. A channel reserved in the last 5 minutes is no longer evicted as missing because a chain read does not show it yet.
- Buyers (`@antseed/buyer-core`): a video's upfront fee is reported as spent (for example to the gateway's ledger) only once the seller has opened its channel, so a video create that never got a channel is no longer billed.
- `@antseed/node`: `BuyerChannelSummary` (and `GET /_antseed/channels`) adds `channelKind` and `live`. `reserveCeiling` is now set only for the live session, not for older channels with the same seller.
- Provider `openai-responses`: a buyer's `max_output_tokens` now reaches the Codex backend instead of being removed. The plugin stripped it as unsupported, but the backend accepts and enforces it (it ends the answer with `status: incomplete`, `reason: max_output_tokens`). Without the cap a model that loops can keep one answer streaming until the backend cuts it off, and the seller records no usage for it. A non-streaming request that reaches the cap gets the partial answer as JSON with `status: incomplete` and `incomplete_details`, instead of the raw event stream.
- CLI gateway: video jobs are counted against a key's spend limits exactly once, from the moment they start until they are charged, instead of blocking keys that had spent nothing. Each create and status poll used to hold the per-request reserve ($0.30 by default) for a minute after it was answered, so polling a few videos refused a $5/day key with `402 spend_limit_reached` with nothing spent. Now:
  - A create tells the buyer how much is left under the key's caps (the lowest of the key's, its owner's and its workspace's) in `x-antseed-max-video-usdc`, and holds that room (at most the buyer's per-video limit, `payments.maxVideoRequestUsdc`, default $5, a new config field the CLI buyer now also applies) while it waits. The buyer refuses a video priced above it with `422` ("Video costs … USDC, more than the … USDC left on this spend limit") before any job starts. Deposits were already checked against the price before the video's payment channel opens. A buyer announces that it checks this (`capabilities: ["video-budget"]` on its attributed-spend feed); through an older buyer, which would start the video regardless, video creates of capped keys answer `503 buyer_upgrade_required` without being sent (keys without caps are unaffected). A capped video create is not held for a restarting buyer (the buyer that comes back may be an older one). Another request that only misses a cap because a video is still being priced answers `429 video_pricing_in_progress` (with `Retry-After`) instead of `402 spend_limit_reached`.
  - An accepted job then holds its price, as reported by the buyer in `x-antseed-video-price-usdc` (never more than the room it was told about; the whole room when the price is missing or unreadable). It is stored in the gateway database (migration 10), so a restart keeps it: a create stores its reservation before it is sent (a capped create whose reservation cannot be stored answers `503 spend_tracking_unavailable` without starting), and the reservation is swapped for the job in one transaction, so a gateway that restarts before storing an accepted job still counts it, at the whole room its create was told about, less whatever the job was already charged (a recovered job that was delivered gets the usual hour for its charge). The job is read from the buyer's answer even when the request log cannot be written. While a job cannot be stored or the stored jobs cannot be read, requests of capped keys answer `503 spend_tracking_unavailable` instead of being admitted against reservations that could be lost. A free video reports a price of 0 and holds nothing. Status polls and the download hold nothing more, and are admitted even when other spend has filled the caps since (the job already covers its charge, and a free or already charged job has none to come). The price stops counting as the buyer's charge for the delivery arrives (a charge lowers it by its amount, and an opening fee the create already paid on the video's channel is not held again), when the buyer retires the job (`x-antseed-video-job-retired`), an hour after a download the buyer accepted as the finished video was never charged, or after 30 days. Jobs of a revoked key stop counting once nothing can charge them (a download admitted before the revocation, or a delivery whose charge has not arrived, keeps the job counted). A key without caps records the price too, so caps added later count its jobs.
  - Only the key that created a video job may retrieve it; another key gets `404 video_route_not_found`, and a job ID another key already owns does not take over that key's job. Spend the buyer reports without a request ID does not lower a job's reservation.
- CLI buyer: a video job that reports `failed` (including a `completed` status with no video) or that its seller no longer has (404/410) is retired once that is saved: later retrieves answer `404 video_route_not_found` without reaching the seller, so it can never be delivered or charged. Retrieves of one job run one at a time; if the retirement cannot be saved, the poll answers a retryable `unknown`. The buyer drops a seller's copy of `x-antseed-video-price-usdc` and `x-antseed-video-job-retired` (in any letter case), and pays a video exactly its price: the 1.4x tolerance for token estimates no longer applies to video charges. A download stream the buyer does not accept as the finished video (too short or unreadable, so not charged) is now cut off instead of ending like a complete download, and the job is retired (the same file would only be rejected again). A buyer that could not read its saved video routes at start no longer reports unknown jobs as retired, since their routes may come back on the next start. A download only counts as the finished video once the buyer has recorded it as the job's delivery and saved that the job is done. If that cannot be saved yet, the seller is still paid for the file, but the download is cut off without retiring the job (`x-antseed-video-delivered: unrecorded`), so a gateway keeps the price held until the charge reaches it and the video can be downloaded again once the save succeeds, after which the job can no longer be charged, also when other requests have meanwhile pushed the download's billing out of the buyer's request cache.

- CLI gateway: when the buyer's answer breaks off mid-stream, the gateway now closes the client's connection instead of leaving it waiting.
- CLI gateway: a request sent while the buyer restarts (an update, or a restart from the console) now waits for the buyer, for up to 2 minutes, instead of failing with `502 buyer_unavailable`; a key with spend caps waits for the buyer's spend feed the same way instead of failing with `503 spend_tracking_unavailable`. Only refused connections are retried, so the buyer never sees a request twice, and a request the buyer never received releases its budget hold at once. On shutdown the gateway and the buyer stop accepting requests and give the ones in flight up to a minute to finish (the buyer used to stop them after 15 s).
- Node buyer: a payment channel that served many different models no longer gets stuck answering every request with `402 payment_required`. Each SpendingAuth carries per-service usage metadata, and the list grew by one entry for every model used on the channel. After about 110 models (for example an agent rotating through image and video models) the SpendingAuth passed the 64 KiB payment frame limit, the seller dropped every later signature, and the buyer kept believing it had paid. The metadata now lists at most 32 services: those already listed keep their own entry, and usage of further services is attributed to one shared "other services" entry (`OTHER_SERVICES_METADATA_ID` in `@antseed/protocol`). Totals and on-chain counters are unchanged. A channel already stuck this way is signed again with the shorter list after the buyer restarts on the new version, and a payment message that would still exceed the limit now fails on the buyer with an error instead of being silently dropped by the seller. Sellers also stop retrying such a channel: when a buyer's SpendingAuth is too large to read, the seller closes the channel at the last signed amount and answers the next request with `channel_exhausted`, so buyers that have not upgraded open a fresh channel instead of staying stuck. The buyer also stops raising its signed amount while the seller keeps asking for the same catch-up: when it has already signed at least what the seller asks for, it resends that authorization unchanged, and if the seller still asks for the same amount it requests a cooperative close, so the channel's reserve is released before a replacement channel is funded. A signed amount above the channel's on-chain deposit (which the contract can never settle) goes straight to that close, with the authorization capped at the deposit. A channel the seller will not close stays active instead of being abandoned with its reserve locked. A seller that blocks a channel it has not accepted any payment on closes it at the on-chain settled amount instead of only forgetting it. A stuck channel previously grew its signed amount on every retry (a $6 reserve showed $30.39 signed in the gateway console) without anything new being delivered; the seller could never claim more than the reserve, but the console showed spend that had not happened.
- CLI gateway: `@preset/<slug>` now applies to every accepted request body, however large, and an alias that cannot be resolved is refused instead of forwarded. The gateway only read a body's model from the first 4 MiB, so a larger one (a chat with a few MiB image attached, which Open WebUI inlines as base64) reached the buyer with the literal `@preset/<slug>` as its model: the buyer answered `502 model_not_found` ("No policy-allowed peer currently serves model \"@preset/…\"") even though sellers within the caps existed, and the request log recorded no model. The gateway now reads the model exactly as the buyer does (`service` before `model`, the whole body, multipart forms included), so the two cannot disagree about which model is bought.
- Node buyer: a stored payment channel that has already ended on-chain no longer blocks new requests to that seller with `409 payment_negotiation_failed` (`existing_channel_still_active`). When several stored channels exist for one seller (for example one left by a reserve that never locked), each is now checked against its own on-chain status and retired once the chain shows it ended, instead of only when the buyer's total reserved balance was zero. A seller's `no_channel` answer to a close request now also retires the buyer's copy, once the chain confirms the channel is no longer open. A channel still open on-chain is kept, so its reserve is never forgotten.
- Node seller: a channel whose close failed three times is no longer abandoned with the buyer's reserve locked. Every 10 minutes the seller retries closing such channels that are still open on-chain, first with the buyer's latest SpendingAuth and, after an hour of failures, at the amount already settled on-chain, which releases the rest of the reserve to the buyer. A channel is retried however long the seller was offline, until it is closed or the chain shows it ended.

- Seller: a provider can list `fallbackUpstreams`, backup upstreams that serve the same models (for example a second account or another host for the same model). - CLI gateway console: the **Not set up yet** notice on the sign-in page points to `antseed gateway console-link` instead of saying `antseed gateway start` printed a setup link.
- CLI: the unused `payments.platformFeeRate` config default is removed; the protocol fee is set on-chain. `AntseedNode`'s `platformFeeRate` option is deprecated and ignored.
- CLI buyer (security): paying as a buyer identity other than the default (the `x-antseed-buyer-identity` header, or `identity` on `POST /_antseed/channels/close`) now requires the gateway control secret (`x-antseed-gateway-auth`) once one exists, so a local client can no longer spend from a workspace wallet by naming it; requests without the secret get `401 gateway_auth_required`. The gateway sends the secret with every request it forwards for a non-default identity. A buyer with no control secret (no gateway on its data dir) keeps accepting identities from loopback callers, and the default identity needs no secret.
- Buyer: automatic routing moves on to the next seller when one answers `model_not_found` (it stopped offering the model, often while busy, and the cached seller list had not caught up), instead of returning that seller's error. This applies to every request, including those without a gateway routing policy. Pinned requests still get the seller's answer.

- Desktop: the balance appears about a second after launch instead of up to a minute later. No seller uses these headers (sellers call their upstream with their own keys), so nothing changes for working setups. ### Added

- Routing: any seller can offer model routing as a paid service. Routing is a service category, not one API: each routing API is its own service API protocol with its own provider plugin and buyer adapter, and none is a default (see "Adding a routing protocol" in `docs/protocol/model-routing.md`). The first is `irp-suggest`, [Inference Routing Protocol](https://github.com/inference-routing/spec/blob/main/SPEC.md) suggest-only mode, unchanged: buyers list a router's models for free (`GET /v1/routing/models`, cached 60s) and pay per ranking (`POST /v1/routing/rank`). The rank request carries the full inference request as an OpenAI Chat Completions body (Anthropic Messages and Responses requests are converted with the existing API adapters) and `routing: { cost_quality_tradeoff, candidates }`. Each candidate has an `id` of the form `provider:model@peer` (hashed when over 128 characters), its `model` (the router's own name for it from the model list, matched to the seller's service ID exactly or by canonical model key, so `claude-opus-5` matches `anthropic/claude-opus-5`), `pricing` (`input`, `cache_read`, `output`; `cache_read` falls back to the input price) and observed prompt-cache reuse as `expected_usage.cache_read_tokens`. The router answers with an IRP `routing.ranking`; the buyer maps each `candidate_id` back through the candidates it sent. IRP paths name no service, so a seller offers at most one `irp-suggest` service and requests are plain IRP with no AntSeed headers (the node refuses to start with two, and buyers skip peers advertising two); errors use IRP problem details, and a 422 refreshes the model list and retries once. A router that lists the model `*` scores any model, so buyers send it every allowed candidate under the seller's service ID. A model entry's optional `max_pricing` (an AntSeed addition IRP clients ignore) stops buyers sending candidates priced above it. See `docs/protocol/model-routing.md`.
- Billing: bill routing ranks as `completed_requests` through the existing unit-billing path, like images. Each routing protocol's wire binding (`RoutingWireProtocol` in `@antseed/protocol/routing`) says which candidates a rank request sent and whether the answer is a usable ranking. Buyer and seller run the same billing adapter on the same request and response, so a well-formed ranking costs one request and a malformed one costs nothing on both sides. Channel top-ups and 402 retries work as for any other paid request. Old buyers ignore sellers that advertise `completed_requests`, so run routing services on separate peers until buyers upgrade.

The `router-local` plugin and `Router` interface are unchanged.
- CLI: route through a selected routing service, by default (`POST /_antseed/route { router: { service, options?, allowedModels? } }`, alongside the unchanged `{ model }`) or per conversation. `options` are the router's settings in its protocol's terms, checked against that protocol when saved and before each ranking (for `irp-suggest`: `cost_quality_tradeoff`, 0 best quality to 10 cheapest; when unset the router's default, 5, applies). `GET /_antseed/routing-services` reports each router's `protocol` and `options`. ### Security

- P2P TCP transport is now encrypted end-to-end (`transport.tcp-enc.v1`): a wallet-signed ephemeral X25519 handshake with forward secrecy and mutual peer authentication, AES-256-GCM framing for all payload traffic. Enabled automatically between peers that advertise the capability in discovery metadata; once offered, the handshake fails closed rather than downgrading to plaintext, and the intro signature covers the advertised capabilities and encryption offer so an on-path attacker cannot strip them to force a legacy fallback. Legacy peers still connect over plaintext unless the new `requireSecureTransport` node option is set.
- WebRTC signaling now signs SDP descriptions (`transport.signed-sdp.v1`), binding the DTLS certificate fingerprint to the peer's wallet identity so a man-in-the-middle on the signaling socket can no longer substitute its own SDP.
