# @antseed/node

The runtime around buyer-core and the plugins: P2P transport and identity, discovery, metering, seller request handling and sqlite. It is the plugin host. `src/interfaces/plugin.ts` and `seller-provider.ts` define what a plugin implements, including `serviceApiProtocols`, and the node does everything else. `seller-request-handler.ts` picks a protocol for billing only and never translates; the buyer proxy (`apps/cli/src/proxy/buyer-proxy.ts`) does that. `src/payments/` re-exports the buyer's payment code from buyer-core; the seller side (`seller-payment-manager.ts`), the sqlite channel store (`channel-store.ts`) and the chain config are node's own.

| Rule | Enforced by |
| --- | --- |
| A schema change is a new numbered migration in `src/storage/migrations/<domain>/`. A shipped one is never edited. | review only; `add-migration` skill |
| Settle-on-disconnect closes at the latest amount the buyer signed. | `tests/payment-flow-integration.test.ts` (that it settles, not the amount) |
| A request the seller bills reaches its provider only as the body the seller wrote from what it priced, naming one service, the one billed, with `x-antseed-service` set to it. | `tests/requested-service.test.ts`, `tests/seller-billed-service.test.ts`, `e2e/tests/seller-serves-billed-service.test.ts` |

The seller reads a request body once to price it (`billedRequestBody` in `src/requested-service.ts`) and hands its provider a body it wrote from what it read: JSON serialized again from the parsed object and labelled `application/json`, and a form written again with the seller's own boundary, one plain `Content-Disposition` per part and a media type on files only. A preamble, an epilogue, part headers, extra disposition parameters and repeated JSON keys never reach a plugin, a relay or an upstream, so they cannot read fields billing did not. The response the seller signs still covers the request as the buyer sent it. Do not add rules for how a parser might read the buyer's bytes; the rewrite covers them.

What a rewrite cannot settle is checked, and refused before payment with a `ServiceRefusal` code: `service` and `model` must agree; a billing input (unit-price match keys, `n`, duration, video options and references, prompt and speech input) is spelled exactly and, in a form, appears once, since a reader that ignores letter case or padding would take `Size` for `size`; a priced image value must be one billing reads (`n` a whole number, `size`, `quality` and `resolution` short plain strings), since billing skips any other and a looser upstream might not (video and speech billing refuse the values they cannot read themselves, as `invalid_billing_request`); and the upstream model selectors the seller knows are refused: the top-level fields `models`, `route`, the `fallbacks` family, `model_list`, `model_group` and `deployment_id`, a path that is not plain characters, a `deployments`, `engines`, `models` or `model` path segment followed by another, and a query parameter naming the service or a billing input. The rewrite does not cover the path, which the relay forwards as it came. The selector lists are best effort: a plugin whose upstream reads other fields or paths that choose a model refuses or removes them itself; add a selector here when one is found. Seller-configured aliases and fallback upstreams must serve the advertised service.

**Ask first:** `src/p2p/identity.ts`, `identity-envelope.ts`, `secure-channel.ts`; a new migration; the plugin interfaces (every plugin implements them).
